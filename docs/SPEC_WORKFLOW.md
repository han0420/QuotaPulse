# Spec-first 开发流程

QuotaDot 的新增功能和用户可见行为调整必须采用 spec-first 模式。规格是行为的来源，测试是规格的可执行证明，实现负责使测试通过。

## 强制顺序

1. **Discover**：阅读 `AGENTS.md`、架构文档、相关现有 spec、代码与测试，确认当前行为。
2. **Specify**：在 `docs/specs/<feature-name>.md` 新建或更新规格；生产代码修改前完成本步骤。
3. **Resolve**：记录假设与取舍。若未决问题会明显改变产品行为，先向用户确认；否则采用最小合理假设并写入 spec。
4. **Test (RED)**：把验收场景写成聚焦测试，运行并确认它因缺少目标行为而失败。
5. **Implement (GREEN)**：完成满足规格的最小实现。
6. **Refactor**：在测试保持通过时整理结构，不扩大规格范围。
7. **Verify**：运行完整测试和安全检查；按风险补充手动验证。
8. **Document**：将 spec 状态改为 `Implemented`，补充实现映射和验证结果；同步其他受影响文档。

不能先实现再补规格或测试。如果发现实现与 spec 冲突，应先判断正确行为并修改其中错误的一方，不能默默保留矛盾。

## Spec 文件规范

文件使用小写 kebab-case，例如 `quota-notification.md`。每份 spec 至少包含以下内容：

```markdown
# 功能名称

- Status: Proposed | Accepted | Implemented | Superseded
- Last updated: YYYY-MM-DD
- Owners: project maintainers

## 背景与目标
为什么需要改变，以及成功后用户获得什么。

## 非目标
明确本次不解决的内容，防止范围漂移。

## 用户行为
从用户视角描述入口、状态和反馈。

## 需求
- R1: 使用可测试、无歧义的 MUST/SHOULD 语句。

## 合法性与边界
输入范围、默认值、迁移、失败和恢复行为。

## 验收场景
- A1 — Given / When / Then。

## 技术方案
组件职责、数据流、持久化和安全影响。

## 测试计划
自动化测试、编译检查和必要的手动测试。

## 实现映射
规格条目对应的源码与测试文件。

## 未决问题
没有则写“无”。
```

## 状态含义

- `Proposed`：正在定义，仍可能发生实质变化。
- `Accepted`：行为边界已确定，可以进入测试和实现。
- `Implemented`：实现、测试和文档均完成。
- `Superseded`：已被另一份 spec 替代，必须链接替代文档。

用户直接提出且边界清晰的实现请求，可由代理在记录合理假设后将 spec 从 `Proposed` 推进到 `Accepted`，无需为形式上的批准中断工作。涉及隐私、安全、破坏性迁移、新服务或明显不同的 UX 方案时，必须先确认关键选择。

## 完成定义

功能只有同时满足以下条件才算完成：

- spec 需求和验收场景均有结论；
- 新行为有自动化测试，且先验证过 RED；
- `swift test` 全部通过；
- `./script/security_check.sh` 通过；
- 英文和简体中文本地化同步；
- 用户可见或架构变化已更新对应文档；
- spec 状态与实现映射已更新。

视觉或系统集成功能无法完全自动化时，在 spec 中列出简短、可重复的手动检查步骤。
